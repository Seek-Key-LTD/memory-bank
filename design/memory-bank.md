## 1. 概述

记忆银行是一个基于 **Shamir 秘密共享 + 智能合约** 的多签密钥管理系统。
通过将主密钥分片分发给多个参与者，由链上合约控制保险柜的开启，实现安全的分布式密钥控制。

核心目标：**没有一个人能单独篡改记忆，必须多人合谋且在规定窗口内才能操作。**

---

## 2. 角色体系

| 角色 | 数量 | 密钥类型 | 权限 | 说明 |
|------|------|----------|------|------|
| **耶稣 (Keeper)** | 1 人 | 持有 T-Key（主控密钥） | 可单独写入 | 一周巡视一次，检查整体信仰状况，可直接 put |
| **十二门徒 (Apostles)** | 12 人 | 持有 Rotation T-Key（轮替分片） | 需 3/5 门限合成 | 每人拿到一个分片，不知道自己拿的是真是假 |

---

## 3. 密钥体系

### 3.1 两种密钥

| 密钥 | 持有者 | 特点 |
|------|--------|------|
| **T-Key（主控密钥）** | 耶稣 | 可直接打开保险柜 put 写入，一周巡视时使用 |
| **Rotation T-Key（轮替分片）** | 十二门徒 | 通过 Vault 注入到各自主机，需 3/5 合成才能打开 |

### 3.2 分片规则

| 项目 | 值 |
|------|-----|
| 总分片数 | 12 |
| 真分片数 | 5 |
| 假分片数 | 7 |
| 恢复门限 | 3（任意 3 个真分片可合成主密钥 Opening Key） |

### 3.3 分片生成流程

```
主密钥 K
    |
    +-- T-Key ── 耶稣持有（可直接 put）
    |
    +-- Shamir Split (t=3, n=5)
    |       +-- 分片 #1 (真) --> 门徒 A (通过 Vault 注入)
    |       +-- 分片 #2 (真) --> 门徒 B (通过 Vault 注入)
    |       +-- 分片 #3 (真) --> 门徒 C (通过 Vault 注入)
    |       +-- 分片 #4 (真) --> 门徒 D (通过 Vault 注入)
    |       +-- 分片 #5 (真) --> 门徒 E (通过 Vault 注入)
    |
    +-- 随机诱饵 (7 个假分片)
            +-- 分片 #6 (假) --> 门徒 F
            +-- ...
            +-- 分片 #12 (假) --> 门徒 L
```

### 3.4 关键特性：门徒不知道自己拿到的是真分片还是假分片

- 分片的外在格式完全一致，无法区分真假
- 只有 Jesus 知道真分片名单
- 门徒在自己的主机上通过 Vault get 到分片，但无法验证是否能打开保险柜
- **只有等到保险柜开启窗口，尝试合成时才知道真假**

## 4. 链上合约 — 保险柜 (Safe Contract)

### 4.1 保险柜核心逻辑

```
合约: MemorySafe
├── 状态: 锁定/开启
├── 开启窗口: 3 分钟（可配置）
├── 开启条件: M-of-N 签名验证通过
├── 写入权限: 开启窗口内可 put
└── 巡视权限: T-Key 持有者（耶稣）可绕过窗口直接 put
```

### 4.2 开启流程

```
     合约锁定状态
          |
    门徒提交分片签名
          |
    合约验证 M-of-N (3/5)
          |
    保险柜开启（3 分钟窗口）
          |
    在此期间执行 put 操作
          |
    窗口关闭，合约重新锁定
```

合约部署在 **Base (Coinbase L2)**，利用 CDP 提供的工具链：

### 4.3 3 分钟窗口内要做的事

1. 门徒们提前准备好要修改的脚本/数据
2. 合约开启后，迅速执行写入
3. 写入完成后验证结果
4. 窗口关闭后任何人都无法再操作

## 5. 日间流程（每日运作）

每天的记忆管理遵循一套固定的流程，称为**日课 (Daily Rite)**。

### 5.1 晨会 — 商量 (Daily Sync)

每天固定时间（如 09:00），十二门徒通过**安全信道**召开晨会：

1. **签到确认** — 确认当日在线人数
2. **议题提出** — 需要修改记忆的成员提出议题
3. **优先级排序** — 大家商量今日要操作哪些记忆
4. **合成决议** — 决定是否需要触发分片合成

> 商量渠道：端到端加密群组（如 Matrix / Signal / 自建 IM）

### 5.2 分片合成 — 多人授权 (M-of-N Signing)

当需要写入记忆时：

```
Step 1: 发起人广播 "需要合成" 请求
Step 2: 持有真分片的门徒各自从本地 Vault get 分片
Step 3: 至少 3 人通过安全信道提交分片签名到合约
Step 4: 合约验证签名，开启 3 分钟窗口
Step 5: 在窗口内执行写入操作
Step 6: 窗口关闭，合约重新锁定
```

### 5.3 每日签到轮值

为了防止分片丢失或持有人失联，设计**分片健康检查**机制：

- 每天随机抽查 2-3 位门徒进行分片持有确认
- 连续 3 天未签到的门徒，触发**分片回收流程**
- 耶稣重新生成受影响的分片，重新分发

### 5.4 日终 — 同步确认

每天结束时：

1. 核对当天的写入记录
2. 确认所有分片状态正常
3. 生成每日操作日志（不可篡改）

## 6. 耶稣巡视机制

### 6.1 巡视周期

耶稣**每周巡视一次**，检查系统的整体健康度。

### 6.2 巡视内容

- 检查门徒的 **faith（信仰）** 是否充足
- 验证 Christianality（整体信任体系）是否稳固
- 审查近期操作日志
- 确认分片持有状态

### 6.3 巡视时的操作

巡视期间，耶稣可以直接使用 **T-Key** 执行 put 操作：

```
耶稣 T-Key
    |
    +-- bypass 合约窗口限制
    +-- 直接 put 写入
    +-- 巡视结束后记录日志
```

## 7. 分发机制

### 7.1 初始分发

耶稣通过以下方式分发分片：

```
耶稣生成分片
    |
    +-- 加密打包（每个分片用对应门徒的公钥加密）
    +-- 注入到每个门徒的本地 Vault 实例
    +-- 门徒通过 vault get 获取分片
    +-- 耶稣销毁本地分片副本（只保留 T-Key）
```

### 7.2 Rotation T-Key 注入流程

每个门徒在自己的主机上运行 Vault/OpenBao：

```
门徒主机
    |
    +-- 本地 Vault 实例
    |       +-- 通过 Infisical export 同步拿到分片
    |       +-- 存储在 Vault 的 secret 引擎中
    |
    +-- vault get secret/rotation-t
    |       +-- 得到分片，但无法判断真假
    |
    +-- 合约开启时提交分片签名
```

### 7.3 分发协议要求

| 要求 | 说明 |
|------|------|
| **前向安全** | 即使信道被窃听，无法解密分片内容 |
| **零知识** | 门徒无法判断自己拿的是真分片还是假分片 |
| **可验证** | 门徒可以验证分片的格式正确，但无法反推 K |
| **不可抵赖** | 分片持有者可签名确认接收 |

### 7.4 再分发（分片更新）

当以下情况发生时，需要重新分发：

- 有门徒离开/失联
- 怀疑某分片泄露
- 定期轮换（如每季度一次）

## 8. 商量与共识机制

### 8.1 讨论流程

```
提案 --> 讨论 --> 表决 --> 准备脚本 --> 触发合约 --> 窗口内执行
```

- **提案**: 任何门徒可发起记忆修改提案
- **讨论**: 在晨会或临时会议上讨论
- **表决**: 简单多数（>50%）通过即可进入合成
- **准备脚本**: 提前准备好要在窗口内执行的写入内容
- **触发合约**: 3 位真分片持有者向合约提交签名
- **窗口内执行**: 3 分钟窗口内完成写入

### 8.2 否决权（耶稣特权）

耶稣对任何提案拥有一票**否决权**，可阻止不合规的操作。

### 8.3 紧急通道

当需要**紧急写入**（如系统修复）时：

1. 耶稣可直接使用 T-Key 绕过合约直接 put 写入
2. 事后在晨会上通报并记录

## 9. 安全模型

### 9.1 威胁模型

| 攻击场景 | 防御措施 |
|----------|----------|
| 单个门徒被收买 | 只有 1 个分片，无法恢复 K，且自己不知道分片真假 |
| 多个门徒合谋少于 3 人 | 门限为 3，不够合成 |
| 耶稣被收买 | 耶稣本就可单独写入，需要通过多人监督机制制衡 |
| 信道被窃听 | 分片用公钥加密传输 |
| 社会工程 | 假分片迷惑攻击者，攻击者无法知道该找谁合谋 |
| 合约攻击 | 3 分钟窗口限制暴露面 |
| 门徒主机被入侵 | 分片存储在本地 Vault，有额外访问控制 |

### 9.2 信任假设

- 耶稣是**可信的初始化者**
- 至少 **3 个真分片持有者不共谋** 才能保证安全
- 安全信道**不被长期监听**
- 链上合约**不可篡改**

## 12. 附录

### 12.1 Shamir 秘密共享原理

Shamir 的秘密共享方案基于多项式插值原理：

- 选择一个 t-1 次多项式 f(x)，其中 f(0) = K（主密钥）
- 生成 n 个点 (i, f(i)) 作为分片
- 任意 t 个点可以唯一确定多项式，从而恢复 K
- 少于 t 个点无法得到任何关于 K 的信息

### 12.2 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 主密钥 | Master Key (K) | 最终的写入凭证 |
| T-Key | Treasury Key | 耶稣持有的主控密钥，可直接 put |
| Rotation T-Key | Rotation Treasury Key | 门徒持有的轮替分片 |
| 分片 | Share/Shard | 密钥的碎片 |
| 门限 | Threshold (t) | 最少需要多少个分片才能恢复 |
| 真分片 | Real Share | 包含真实密钥材料的分片 |
| 假分片 | Decoy Share | 诱饵分片，无法恢复密钥 |
| 合成 | Combine/Recover | 将分片合成为主密钥的过程 |
| 保险柜 | Safe Contract | 链上合约，控制开启窗口 |
| 日课 | Daily Rite | 每日固定的操作流程 |
| 巡视 | Inspection | 耶稣每周一次的整体检查 |
